# External screen shortcut bar · Project collaboration rules

## Project and document entry

-Android source code, resources and tests are located in `app/`, and Gradle configuration is located in the root directory; `docs/` saves the development process and module contract, `dist/` saves the final delivery, release notes and independent HTML prototypes, `tools/` saves independent auxiliary tools.
-`README.md` only introduces the software positioning, usage and functions, and the permissions and compatibility boundaries are explained from the user's perspective. `AGENTS.md` only maintains stable structure, responsibility boundaries, hard constraints and completion standards; implementation parameters, operating procedures, acceptance records and historical issues are written into corresponding documents.
-The current entry for building, signing, legacy migration and verification is [Development Notes](docs/development.md)，The usage and authorization entrance is [Instructions for use](docs/getting-started.md)。History does not replace the current build configuration.
-Single maintenance can be submitted directly to `main`, and PR is not required; main is prohibited from force push and deletion, and normal push is allowed; see [Engineering Process] for boundaries of engineering inspection, temporary storage review, push and independent release.(docs/engineering-workflow.md)。`tools/project/` Unified warehouse, static website and APK delivery check, CI uses the same entrance.
-Read before modifying the module[module contract](docs/module-contracts.md) Relevant chapters and its special documents; specific functional constraints have been moved into this document, and organizing AGENTS does not mean lifting the original constraints. Behavior changes synchronously update their corresponding contracts to avoid duplication or conflicting rules.

## The only source of configuration and data

- `app-config.json` To focus on frequently used adjustments, press `update`、`defaults`、`appearance`、`motion` Grouping, checksum generation by `gradle/app-config.gradle` manage,`AppConfig` Read; rebuild after modification to take effect. User preferences take precedence over default values.
-The package name, version, SDK and dependencies remain in Gradle; the fixed grid, security constraints, internal cache limit and algorithm remain in the corresponding module, and the key is stored independently. The shared style class is responsible for calculation and dual-host adaptation, and generating constants and resources does not become a second configuration source. See details[Configuration instructions](docs/app-configuration.md)。
- `Prefs` and `AppWorkspaceLayout` Is the sole source of persistent data for the launcher；`AppLauncherStyle` Is the only source of common dimensions and geometry for both launchers. Public functions, data and styles are modified in the shared layer and check the floating windowand native cards, and does not maintain the second preference.
- The draft is only changed after valid operations and is saved atomically after completion; return, cancel, disconnect and uninstall are released according to the corresponding session. The configuration import first verifies the layout, capacity, unique ownership and overlap, and retains the local monitor selection, permissions and system display settings; the identity of the device and component binding is not entered into the backup.

## Boundaries that must be maintained

-Monitor-specific operations only use the secondary screen selected by the user or reliably recognized, and never silently return to the main screen 0; system-wide switches are clearly marked. The application direction rule is only executed once when the tool is explicitly started. After asynchronous completion, the target external screen is re-verified. The direction is not forced by foreground events.
-The external screen multi-tasking page can display the user's internal screen, the selected external screen and recent unmounted tasks, retaining the true source; the internal screen card only displays the application icon, with the small letters "(internal screen)" added after the name, and does not read the screenshots of its tasks, and no status text is displayed under all cards. Only when the user clicks the card, the original task will be restored to the selected external screen; explicitly closing the task page can affect the listed internal screen tasks. The Dock is still limited to the selected external screen and does not extend to other secondary screens or users.
-Permissions are controlled by the user; no automatic authorization, no lock screen bypass, no root, driver or arbitrary shell capabilities added. `ShellService` remains in the restricted Shizuku whitelist, and `ShizukuBridge` manages connections and background calls; it does not pretend success or return to the home screen when the system rejects the operation.
-Does not read other application page node trees, does not inject system input, and does not persist notifications or usage history. Foreground judgment only uses the selected external screen window metadata and event package name; notifications, recent tasks and snapshots are only used within necessary visible sessions, and are released promptly when identity changes or the session ends.
-Internet access is limited to user-initiated online update checks and downloads. Notifications, configurations or device information are not uploaded, and analysis and tracking are not added. Complete update files and signature certificates are verified, and the installation is confirmed by the system. System Control Center restricts selection to stay on this machine only.
-The two hosts of the launcher are fixed with 5 columns and 3 rows, and 15 cells per page; the application has the same width and height, and the folder has a 2×2 logical placeholder. The normal control center uses `Prefs.panelColumns` to manage the 3/4/5 column and 4-row viewports. The editing page is arranged independently and compactly without rewriting the normal column number or display DPI.
-The shortcut bar drawing and touch range are outside the page boundary in four directions, automatic and manual safe zones; the page text will not be narrowed or raised again due to the shortcut bar, and the real gap is always avoided. For the treatment of insufficient space on the boundary and outside, see [Safe Zone Contract](docs/safe-area.md)。
-Double white bars are always horizontal, left notification, right control: 0° top left or bottom right, 180° top left, 90°/270° top left or top right. Each interface of the assistant unifies the consumption safety zone; the automatic mode follows the system edge lining, and the manual mode replaces the adjustable boundary according to the current direction, both of which avoid real gaps. Calibration rotation must be confirmed by the user and restored to the original state when completed; it does not restore the side vertical alignment, does not mirror the notch, does not claim to disable system gestures or write the global navigation policy.
-The status bar is shown and hidden by application only to control the selected external screen status bar drawn by the assistant. The unknown front desk is displayed by default, and the empty list disables the corresponding judgment; the control center status line is independent and does not control the system's native bar.
-Public windows, subscriptions, callbacks, icons, snapshots, inputs and animations follow the mount and session life cycle; closing, screen off, out of focus, disconnection and uninstall cancel old work, and late callbacks cannot restore old sessions. Avoid background polling, resampling, and window rebuilding for content updates.
-The setting update does not modify the runtime floating layer through the global `Ui`; the setting zoom does not access the combination card configuration. At runtime, the materials and animations only change the drawing, maintaining the existing static geometry and touch range; the public container cancels the multi-finger sequence before the sub-control event is split.
-Design, refactor, prototype and review of Settings UI using [oneui-settings-design](.agents/skills/oneui-settings-design/SKILL.md)，Refer to `mobile-android-design` for its collaboration rules; themes do not automatically extend to runtime overlays or system selectors. For the migration entry, see [Setting Plan](docs/settings-ui-refactor-plan.md)。
- Third-party APKs are entered for reference only and may not be modified, replaced, re-signed, or redistributed. `tools/notification-tester/` is an independent test App. It only manages its own notifications, does not rely on or modify the main application, and does not automatically authorize; see the entrance.[README](tools/notification-tester/README.md)。

## Signature, Delivery and Completion Standards

-Debug and Release share the official signature specified by the package names `io.github.flipcover.controls` and `keystore.properties`; no key allows compilation, unit testing and lint, and all APK/AAB packaging must have a formal signature; new versions increment `versionCode` and do not restore the `.debug` suffix or the default debug signature. Keys and passwords are not stored in the database and must be backed up independently and securely.
-The cloud APK is only triggered by the version tag from main that is consistent with the Gradle version; the official signature uses the `android-release` environment Secrets, and ordinary CI does not use the private key. Release only delivers verified public products and does not cover released assets; cloud packages that have not completed device acceptance are marked as pre-release. See the entrance [Engineering Process](docs/engineering-workflow.md)。
- The APK is delivered to `dist/update-release/<versionCode>/flipcover-<versionName>.apk` or `dist/update-debug/<versionCode>/flipcover-<versionName>-debug.apk`, with the actual metadata, size and SHA-256 corresponding `catalog.json` in the same directory; `dist/update-debug/` and `dist/update-release/` The entire directory is only kept local and ignored by Git, including catalog, manifest and release notes; Release uses `:app:prepareUpdateRelease`. Testing the lower version only temporarily overwrites the build version, and does not reduce the official version, cover the released directory, or automatically move historical products.
-`dist/` The final UI rendering must be superimposed once on the top layer `dist/device-frames/zflip5-cover-overlay.svg` or the corresponding transparent PNG, press [Texture Description](dist/device-frames/README.md) Align and retain the frame, dual cameras and flash; the directions are rotated synchronously without duplication, stretching or mirroring. Unsynthesized screenshots are only used as original verification materials.
-The HTML prototype and required static resources are uniformly tiled and delivered to `dist/html/`. The files in the directory use relative paths to the same directory and can be uploaded to the static server as a whole; the device map copy is generated by `tools/device-frames/build.mjs` from the only source `dist/device-frames/`; the file entry is clear, and the display and existing interaction are verified in a common browser, without relying on the Codex environment or the machine's private path.
-Completed work must have a successful build and related local checks, indicating local, simulator and physical real machine evidence and unverified items respectively; prototypes and simulators cannot replace Samsung firmware window routing, native host and lock screen compatibility acceptance. For detailed procedures, see [Development Notes](docs/development.md)。
- `Cache/build-output.nosync/app/`：Gradle All application products and reports are managed by Gradle configuration, can be rebuilt, are not stored in the database, and cannot be used as the final delivery entry.
-`Cache/build-output.nosync/project/`: Temporary files for website assembly, test fixtures and release preparation of engineering tools, managed by `tools/project/`, can be rebuilt and not stored in the library.
-`Cache/build-tools/` and `Cache/sdk/`: Disposable native build tools from the official supplier, which are managed by the native environment and are not stored in the library; source code and build configuration must not rely on machine-specific content. Other temporary evidence is stored in Cache by task and is not written to AGENTS.
